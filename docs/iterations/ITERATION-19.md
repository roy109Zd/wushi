# ITERATION 19 · 3DGS 街景打开优化

- 日期：2026-11-02
- 触发原因：推门进入街市时等待明显，怀疑是性能问题。
- 结论：**是问题**。7.9MB 场景本身不大，慢在 3DGS 查看器的初始化与泼溅排序；CPU 环境下更明显。

---

## 1. 慢在哪

| 环节 | 成本 | 说明 |
|---|---|---|
| 下载 `street.spz` | 7.9MB | 本地服务很快，弱网才明显 |
| 建 Viewer | 中 | 新建 WebGL 上下文、worker、shader 编译 |
| `addSplatScene` | **高** | 解析 splat、上传 GPU、按深度排序；CPU 渲染时每帧排序很重 |
| 首帧 | 高 | 着色器编译 + 排序同时发生 |

无头浏览器（纯 CPU、swiftshader）实测：**20 秒超时仍未就绪**。

## 2. 已做的优化

1. **空闲预取**：首屏 6 秒后用 `fetch(..., {cache:'force-cache'})` 把 7.9MB 抓进缓存，控制台会打印「已预取 7.9MB」；
2. **加载层**：进入街市时显示「正在进入街市 / 正在初始化 3DGS 渲染器」，不再是黑屏；
3. **超时回退**：20 秒未就绪则关闭街景、提示「加载失败或超时，已留在街市」，回到漫游；
4. **二次打开免加载**：Viewer 与场景保留在内存，返回后再进是即时的；
5. 关闭时不再重复创建 Viewer。

## 3. 仍不够的原因

3DGS 是「每帧对可见泼溅排序」的渲染方式，纯 CPU 下几乎不可用。即使预取，初始化与排序也无法省掉。

## 4. 下一步建议

- **全景兜底**：World API 同时返回了 `panoUrl`（等距柱状全景图）。把它做成「拖拽环视」的全景查看器，加载只要 1–2MB、秒开，作为 3DGS 的替代或降级方案；
- **降低泼溅数量**：用 LOD 或离线抽稀 `.spz`，代价是清晰度；
- **只在有独显时启用 3DGS**：用 `renderer.getContext().getParameter(UNMASKED_RENDERER_WEBGL)` 判断，软件渲染直接走全景。

## 5. 如何验证优化

打开控制台，推门后看两条日志：

```text
[SplatStreet] 已预取 7.9MB
[SplatStreet] ready in xxxx ms
```

`ready in` 就是真实初始化耗时；若超过 10 秒，建议直接切全景方案。
